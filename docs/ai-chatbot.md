# GPU 기반 AI 챗봇 인프라

2026년 8월부터 학사 정보를 제공하는 AI 챗봇 서비스를 구축하고 있습니다. 본인은 전체 서비스 구조와 GPU 장비의 실행 환경, 기존 클라우드와의 연결을 담당합니다. 동료 1명은 LLM 관련 설계를 담당합니다.

기본 Kubernetes·네트워크·Local PV 기능을 검증했으며, Gateway·모델·애플리케이션·외부 DB의 서비스 통합은 진행 중입니다.

## 담당 역할

| 담당 | 범위 |
|---|---|
| 본인 | 전체 서비스 구조, 포털 접속과 연계 방식, GPU Kubernetes·네트워크·스토리지, 외부 데이터 인프라 연결 설계와 통합 |
| 동료 1명 | LLM 관련 설계 |

## 독립 GPU 클러스터 구축

GPU 장비는 별도 단일 노드 bare-metal Kubernetes로 구성했습니다. Nova compute나 CAPI/CAPO가 생성하는 가상머신, 기존 관리 Kubernetes의 worker로 편입하지 않고 가상화 자원 제공 영역과 GPU 실행 영역을 분리했습니다.

기존 관리 영역에서 GPU Kubernetes API로 연결하는 경로를 검증했습니다. 2026년 9월 1일 기록에서는 기본 클러스터와 단일 노드 Pod·Service·DNS 통신, static/dynamic Local PV 기능을 확인했습니다. 단일 물리 노드 장애에 대한 고가용성은 제공하지 않습니다.

## 서비스 요청과 데이터 연결 설계

기존 포털을 사용자 진입점으로 두고, 관리 영역의 Gateway에서 GPU 클러스터의 챗봇 frontend/backend로 요청을 연결하도록 설계했습니다. [서비스 연계 구조도](../diagrams/03-openstack-kubernetes-gpu.md)에서 기반 검증을 마친 연결과 통합 중인 요청 경로를 구분했습니다.

모델 파일은 Local SSD에 보존해 Pod 재생성이나 이미 확보한 모델로 전환할 때 반복적인 네트워크 전송을 줄이도록 설계했습니다. AI DB는 GPU 장비 밖의 OpenStack에 별도로 배치하는 설계입니다. 모델·앱과 외부 DB의 실제 서비스 통합은 진행 중이며, 모델 재사용 설계를 추론 속도 개선 실측값으로 사용하지 않습니다.

## 데이터 최신성에 대한 협의

크롤링 결과를 저장하면 다시 수집하지 않고 빠르게 조회할 수 있다는 동료의 의견을 검토했습니다. 대상이 수시로 변하는 공지사항이라는 점을 함께 논의하고, 최신 정보를 제공하는 목적을 우선해 크롤링 결과를 영구 저장하지 않기로 합의했습니다. 이 합의는 해당 크롤링 결과에 관한 것으로, 다른 RAG 데이터나 서비스 DB 전체에 적용하는 정책은 아닙니다.

## 다음 통합과 검증

포털에서 Gateway를 거쳐 모델 응답까지 이어지는 전체 요청 흐름, 외부 DB 연결과 모델·애플리케이션 배포 후 동작을 검증할 예정입니다. 8월 26일 설계 기록의 vLLM·Qwen3, pgvector·HNSW, RAG·Rule Engine·MCP는 후보·구성 검토 항목으로, 최종 채택과 실제 서빙 결과는 추가 확인 범위입니다.
