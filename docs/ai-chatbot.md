# GPU 기반 AI 챗봇 인프라

[README](../README.md#구조도와-상세-문서)

2026년 8월부터 학사 정보를 제공하는 AI 챗봇의 인프라 구축과 서비스 연계 설계를 수행했습니다. 본인은 전체 서비스 구조와 GPU 장비의 실행 환경, 기존 클라우드와의 연결을 담당합니다. 동료 1명은 LLM 관련 설계를 담당합니다.

기본 Kubernetes·네트워크·Local PV 기능 검증에 이어, **2026-10-21에 G5 데이터 기반의 합의된 구축·검증·정리를 완료했습니다.** G5는 이 프로젝트에서 DNS·etcd·PostgreSQL HA와 DGX 접속 경로를 확인하는 단계 이름입니다.

PostgreSQL 두 노드와 etcd 세 멤버를 구성하고, 계획 전환·watchdog reset·Primary 종료 유지·강제 재부팅을 서로 다른 시험으로 검증했습니다. DGX 일반 Pod에서 같은 DB 서비스 이름으로 TLS와 클라이언트 인증, 합성 9행 조회를 확인한 뒤 임시 DB·계정·HBA 규칙과 Pod를 정리했습니다. [G5 사례 문서](g5-postgresql-ha.md)에 설계 이유, 구조도, 실패와 보정, 검증 한계를 정리했습니다. Portal부터 모델 응답까지의 전체 AI 서비스 통합은 후속입니다.

## 독립 GPU 클러스터 구축

GPU 장비는 별도 단일 노드 bare-metal Kubernetes로 구성했습니다. Nova compute나 CAPI/CAPO가 생성하는 가상머신, 기존 관리 Kubernetes의 worker로 편입하지 않고 가상화 자원 제공 영역과 GPU 실행 영역을 분리했습니다.

기존 관리 영역에서 GPU Kubernetes API로 연결하는 경로를 검증했습니다. 2026년 9월 1일 기록에서는 기본 클러스터와 단일 노드 Pod·Service·DNS 통신, static/dynamic Local PV 기능을 확인했습니다. 단일 물리 노드 장애에 대한 고가용성은 제공하지 않습니다.

## 서비스 요청과 데이터 연결 설계

기존 포털을 사용자 진입점으로 두고, 관리 영역의 Gateway에서 GPU 클러스터의 챗봇 frontend/backend로 요청을 연결하도록 설계했습니다. [서비스 연계 구조도](../diagrams/03-openstack-kubernetes-gpu.md)에서 기반 기능을 검증한 연결과 서비스 연계 설계·통합 범위를 구분했습니다. [전체 구조와 처리 흐름](ai-chatbot-architecture.md)은 2026-10-16 설계와 10월 21일 데이터 기반 완료 상태를 공개용 역할명으로 정리한 그림 7개이며, 미결정 사항·구현 연기·공개 생략을 구분합니다.

모델 파일은 Local SSD에 보존해 Pod 재생성이나 이미 확보한 모델로 전환할 때 반복적인 네트워크 전송을 줄이도록 설계했습니다. AI PostgreSQL은 GPU 장비 밖의 OpenStack VM 두 대에 배치했고, DGX 검증 Pod의 실제 접속까지 확인했습니다. 애플리케이션 전용 DB·계정과 PgBouncer 연동은 후속입니다. 모델 재사용 설계를 추론 속도 개선 실측값으로 사용하지 않습니다.

## 외부 데이터 기반 구축과 인증 검증

내부 권한 DNS 두 대와 내부·외부 이름 해석 분기를 준비하고, etcd 3멤버의 TLS 연결과 건강성을 확인했습니다. peer·server·관리 client 신원을 구분하며, 관리 인증과 별개로 Patroni용 계정 두 개에 독립 비밀번호와 공통 prefix 제한 역할을 적용했습니다.

2026-10-13에는 etcd VM 내부에서 두 계정의 정상·오류 비밀번호 경로, 허용 prefix 읽기, 범위 밖 읽기와 관리 접근 거부를 검증했습니다. 승인된 시험 키에 대한 조건부 생성·값과 revision 대조·조건부 삭제·최종 부재 확인도 완료했습니다. 이 10월 13일 시험 자체는 실제 DB VM 연결이나 장애 전환 완료를 뜻하지 않습니다. 이후 실증은 아래 날짜별 기록으로 구분합니다.

[AI 데이터 기반의 설계와 동작](ai-data-foundation-flow.md)에서 전체 구조, DNS 경로, TLS와 권한의 차이, Ansible 실행 위치, 조건부 검증 절차를 그림으로 설명합니다.

## DB 서비스의 실증과 마감 — 2026-10-18~21

10월 18일에는 소량 합성 벡터의 저장·거리순 검색과 HNSW 생성·사용, 양쪽 노드의 데이터·인덱스 반영을 확인했습니다. 작은 자료에서 세션 내 순차 스캔을 억제한 시험이며 기본 실행계획·ANN 성능·검색 품질 검증은 아닙니다.

19일의 짧은 watchdog 시험에서는 실제 reset·재부팅과 DB 접속 복귀를 확인했지만 기대한 다른 노드의 자동 승격은 검증하지 못했습니다. 별도 승인한 20일의 종료 유지 시나리오에서는 수동 승격 없이 다른 Primary·동일 DB 접속점의 TLS 읽기·쓰기·Replica 재합류와 복제를 확인했습니다. 이어 강제 재부팅 시험에서는 동일 Primary의 복구·데이터 보존과 새 쓰기·복제를 확인했으며, 이를 자동 승격 성공으로 세지 않습니다. 조기 종료한 관측 시간과 미확정 실패 계층도 [시나리오별 결과](validation.md#database-validation-20261018-20)에 남겼습니다.

20일 DGX 일반 Pod의 DNS·TCP와 실제 출발 주소를 관측한 뒤, 클라이언트 인증서·비밀번호를 이용한 DB TLS·SQL 검증까지 완료했습니다. LB와 보안그룹은 확인한 제어 호스트와 DGX 노드의 두 단일 주소만 허용하고, 변경 후 양쪽 클라이언트의 9행 조회를 재검증했습니다.

21일에는 임시 HBA 규칙·검증 DB·계정의 삭제와 양쪽 반영을 확인했습니다. 최종 상태는 DB VM B가 Primary, A가 Replica이며 TLS 비동기 복제, etcd 세 멤버 건강성, LB의 Primary 선별과 접근 제한을 확인했습니다. 이 역할 배치는 당시 관측이며 역할을 이름에 고정한 설계가 아닙니다. DB 실증은 전체 AI 서비스·장기 안정성·백업 복원·운영 인수 완료와 구분합니다.

## 데이터 최신성에 대한 협의

크롤링 결과를 저장하면 다시 수집하지 않고 빠르게 조회할 수 있다는 동료의 의견을 검토했습니다. 대상이 수시로 변하는 공지사항이라는 점을 함께 논의하고, 최신 정보를 제공하는 목적을 우선해 크롤링 결과를 영구 저장하지 않기로 합의했습니다. 이 합의는 해당 크롤링 결과에 관한 것으로, 다른 RAG 데이터나 서비스 DB 전체에 적용하는 정책은 아닙니다.

## 서비스 통합 확인 범위

DGX 검증 Pod에서 DB TLS·인증·SQL로 이어지는 경로는 확인했습니다. 포털에서 Gateway를 거쳐 모델 응답까지 이어지는 전체 요청 흐름과 실제 모델·애플리케이션 배포 후 동작은 아직 확인하지 않았습니다. 2026년 8월 26일 기록의 vLLM·Qwen3 등 모델·추론 엔진과 HNSW 세부 설정은 최종 채택으로 표시하지 않습니다. 후속 결정에서는 애플리케이션 8종의 독립 Deployment, CPU RAG·Embedding, 초기 LLM GPU 2장, PostgreSQL·pgvector 및 MCP Tool Gateway의 역할 경계를 확정했습니다. 세부 API 계약·검색과 권한 검사 담당·모델 선택은 TBD로 두며, 설계 확정을 실제 서빙·응답 품질·처리량·지연 검증으로 확대하지 않습니다.

[검증 결과](validation.md)에 기반 구축과 전체 서비스 통합의 범위를 정리했습니다.
