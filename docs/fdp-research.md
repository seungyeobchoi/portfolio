# FDP SSD 파일시스템 인터페이스 연구

## 연구 목적

연구 환경에서 FDP SSD를 파일시스템 위에서 활용할 수 있도록 Linux 커널의 I/O 경로를 확장했습니다. 응용 프로그램의 I/O 호출에 배치 정보인 PLI(Placement Identifier)를 추가해 기존 ext4를 유지하면서 장치까지 전달하는 것이 목표였습니다. 수정된 커널과 FDP 지원 장치가 필요합니다.

## 연구의 확장

초기에는 MySQL InnoDB 쓰기 경로와 NVMe 명세를 분석하고 NVMe Passthru 기반 쓰기를 구현했습니다. 파일시스템을 우회하는 방식으로 기존 I/O를 모두 대체하기 어렵다는 한계를 확인해 커널·파일시스템 계층으로 연구를 확장했습니다.

신규 시스템 콜과 VFS·ext4·Block Layer·NVMe 드라이버의 전달 경로를 수정했습니다. 응용 프로그램부터 장치까지 PLI를 유지하고, 다른 PLI의 요청이 병합되지 않도록 처리했습니다. 응용 프로그램을 전혀 수정하지 않아도 된다는 의미는 아닙니다.

검증 중 FDP 정보가 반영되지 않는 현상은 계층별 로그와 플래그 정의를 대조하여 분석했습니다. 신규 플래그 값이 기존 커널 플래그와 충돌하는 원인을 찾아 수정했습니다.

## 실제 장치 실험

학위논문 표 8~14, 그림 18~19와 본문 41~52쪽을 기준으로 요약했습니다. 초기 MySQL Passthru 연구 결과와 아래 커널 인터페이스 실험을 혼합하지 않습니다.

환경: Ubuntu 24.04, 수정 Linux 6.8.12·ext4, MySQL 8.4, go-tpc TPC-C, warehouse 1,000, threads 640, buffer pool 10 GB. Namespace 1은 256 GiB, 사용 RUH는 7개입니다.

| 실험 | 배치 기준 | 평균 TPM |
|---|---|---:|
| Vanilla_fdp_off | 무변형 MySQL, FDP 비활성 | 144,527.85 |
| Vanilla_fdp_on | 무변형 MySQL, FDP 활성 | 167,372.85 |
| A | InnoDB 파일 역할 | 76,333.41 |
| B | 쓰기 요청·데이터 총량 | 105,306.34 |
| C | 오프셋 쓰기 집중도 | 76,154.36 |
| D | 파일 크기 변화량 | 87,865.91 |
| DBLWR | 더블라이트 파일만 별도 배치 | 165,325.27 |

WAF는 매체 쓰기량을 호스트 쓰기량으로 나눈 값입니다. FDP 카운터에서는 `MBMW / HBMW`를 사용했습니다. 배치 전략들의 Prepare 이후 Run 완료까지 WAF 증가량은 Vanilla_fdp_off보다 28~40% 작았습니다. 최종 WAF 자체가 28~40% 감소했다는 의미가 아닙니다.

## 결과와 해석의 구분

측정 결과 A~D는 두 Vanilla보다 TPM이 낮았습니다. DBLWR은 Vanilla_fdp_on에 근접했습니다. 따라서 WAF 개선을 모든 전략의 처리량 향상으로 일반화하지 않습니다.

논문에서는 서로 다른 PLI 간 병합 제한, 요청 분할과 큐 공유가 호스트 처리 비용을 증가시켰을 가능성을 제시했습니다. 병합률과 큐 지연을 직접 측정해 인과관계를 확정한 결과는 아닙니다. PLI별 큐 처리와 배치 정책 개선은 후속 연구 방향입니다.

이 경험을 통해 개별 저장장치 지표와 응용 프로그램 처리량을 함께 확인하고, 응용 프로그램·커널·장치를 연결한 I/O 경로에서 성능을 해석하는 관점을 익혔습니다.
