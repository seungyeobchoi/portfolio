# 인프라 설계 판단

[README](../README.md#구조도와-상세-문서) · 프로젝트 소개: [클라우드](cloud-platform.md) · [AI 챗봇](ai-chatbot.md)

보유 장비와 변경 권한의 제약을 확인하고, 기존 연결을 유지하면서 필요한 기능을 추가하는 방향으로 설계했습니다. 다음은 선택의 이유와 기록에서 확인한 결과입니다. 적용·기능 검증과 서비스 연계 설계를 구분하며, 시점별 결과는 [검증 기록](validation.md)에 정리했습니다.

## 외부망과 내부망 분리

서버의 NIC·CPU·RAM·SSD와 기존 스위치 사양을 검토했습니다. 기존 1GbE 스위치에 Ceph 복제·스토리지 I/O·API 트래픽이 집중될 가능성을 고려해, 외부 접속 경로는 유지하고 별도 10GbE 내부망을 구성했습니다. 통신 경로를 분리한 결과이며 실측 처리량 향상률은 제시하지 않습니다.

## 기존 구성을 유지한 Octavia 관리망 확장

Neutron 논리망은 있었지만 Controller와 Amphora 사이의 관리 L2 경로가 미완성이었습니다. 처음에는 내부망 구조 변경 부담 때문에 외부망 활용을 검토했습니다. 서버실 담당자에게 문의했으나 외부 업체가 설치한 스위치의 관리자 정보를 확보할 수 없어 필요한 설정을 할 수 없었습니다.

서버 NIC와 스위치 포트, 기존 관리망·VXLAN 경로를 다시 확인했습니다. 기존 외부망의 Linux bridge·veth·OVS 연결 방식을 참고하면 관리 IP와 VXLAN 경로를 유지한 채 내부망에 Octavia 관리용 VLAN 경로를 추가할 수 있었습니다.

Linux VLAN 인터페이스에서 태그를 처리한 뒤 Linux bridge·veth를 거쳐 OVS에 연결했습니다. 따라서 Neutron에서는 별도 physnet의 flat 네트워크로 표현합니다. 실제 적용 구조는 [네트워크 구조도](../diagrams/04-network.md)에 정리했습니다.

2026년 8월 14일 시험용 로드밸런서의 생성과 ACTIVE·ONLINE 상태, 삭제 후 임시 자원 정리를 확인했습니다. 검증 범위는 해당 관리 경로와 시험용 자원의 동작이며, 전체 기존 서비스의 무중단을 보장하는 결과는 아닙니다.

## 독립된 GPU 클러스터

GPU 장비는 별도 단일 노드 Kubernetes로 구성했습니다. 가상화 기반 자원 제공 영역과 GPU 실행 영역을 분리하고 관리·서비스 경로를 연결하는 방식입니다. GPU 장비는 Nova compute나 기존 관리 클러스터의 worker로 편입하지 않았습니다.

기본 클러스터와 API 경로를 검증했습니다. 2026년 9월 1일 기록에서 Pod·Service·DNS 통신 및 Local PV 기능도 확인했습니다. 단일 물리 노드 구성이므로 노드 장애에 대한 고가용성은 제공하지 않습니다.

## 모델 파일과 서비스 DB의 저장 위치

이미 확보한 모델 파일은 Local SSD에 보존해 재사용할 때 대용량 파일을 반복 전송하지 않도록 설계했습니다. AI PostgreSQL은 외부 OpenStack VM 두 대에 분리 배치했고 G5에서 DGX 검증 Pod의 DB 요청을 확인했습니다. DB 요청에는 네트워크 통신이 필요합니다. 모델·DB의 실제 서비스 통합 결과는 미확인 범위이며 추론 속도 개선을 실측한 결과는 아닙니다.

## 검사 출발점과 실제 사용자 경로를 함께 검증

21일 Windows 로그인 뒤 API가 내부 인증 이름을 해석하지 못한 사례에서 관리망의 준비 검사와 사용자 CP 출발 인증 경로를 구분했다. 후속 구현은 CP 한정 DNS와 공개 인증 관측을 추가하고 최초 신뢰·현재 보안·일시 가용성을 분리했다. 과거 성공이나 timeout을 새 허가 근거로 재사용하지 않는 조건을 유지했다.

28일 backend·worker·publisher·프론트 적용 뒤 시험 계정의 Windows·단일 Standard를 생성해 실제 접속·앱·권한 거절·읽기 전용 볼륨·token 자동 갱신·정상 삭제를 확인했다. 직전 초기 권한 설치 실패의 원인은 미확정으로 남겼으며 최종 성공만으로 특정 보정의 필요성을 증명했다고 쓰지 않는다. [검증 결과와 한계](validation.md#standard-user-e2e-20261028)에 구현·배포·종단 시험을 구분했다.

## Registry의 생존·준비 상태와 프로토콜 검증을 분리

격리 Nginx에서 잘못된 시험 인증서로 TLS가 실패해도 HTTP 생존·준비 응답이 모두 200인 상태를 관측했습니다. 프로세스가 살아 있다는 조건과 사용자가 인증된 HTTPS로 Registry에 도달할 수 있다는 조건을 분리했습니다. liveness는 자체 응답, readiness는 CA·이름 검증 HTTPS와 backend 응답으로 보정한 뒤 오류 NotReady·복원 Ready 전환을 재시작 없이 확인했습니다. 인증서 오류에서 이전 인증서를 자동 유지하거나 모든 갱신 실패를 복구한다고 주장하지 않습니다.

합성 응답 서버의 인증 검사 뒤에는 실제 Registry 이미지를 같은 임시 Pod에 넣어 단계적 업로드·manifest/blob 정합성과 읽기 역할의 쓰기 거절을 시험했습니다. backend의 manifest 삭제 미지원과 업로드 취소 허용도 구분했습니다. 앞단의 생존·권한 검사 성공만으로 전체 Registry API나 독립 containerd pull을 성공으로 계산하지 않았습니다.

이는 작은 격리 fixture의 설계·보정 근거입니다. 운영 Registry·소비자 인증 전환·실제 image pull/build·영구 데이터 복구·자동 교체는 후속이며, [날짜별 검증](validation.md#registry-isolated-20261101-02)에 실제 수행과 제외 범위를 남겼습니다.

## 공지사항의 최신성을 우선한 처리

동료와 크롤링 결과를 저장했을 때의 조회 효율을 검토했습니다. 대상인 공지사항이 수시로 바뀐다는 점을 논의하고, 최신 정보를 제공하는 목적을 우선해 크롤링 결과를 영구 저장하지 않기로 합의했습니다. 이 결정은 해당 크롤링 결과의 처리 정책이며, 다른 RAG 데이터나 서비스 DB 전체의 저장 정책과 구분합니다.

## DB 리더 조정·연결 선택·watchdog를 분리

PostgreSQL Primary를 결정하는 Patroni·etcd, 새 클라이언트 연결을 현재 Primary로 보내는 Octavia, Patroni가 watchdog 갱신을 멈추면 VM을 reset하는 장치를 서로 다른 책임으로 구성했습니다. TCP 포트가 열려 있다는 조건만으로 쓰기 노드를 고르지 않고 `/primary`의 역할 판정을 사용했습니다.

짧은 watchdog 시험에서는 실제 reset 뒤 같은 노드가 Primary로 복귀했습니다. 이를 다른 노드 자동 승격의 성공으로 처리하지 않고, 별도의 Primary 종료 유지 시험으로 자동 승격·기존 노드 Replica 재합류·새 쓰기 복제를 확인했습니다. 두 DB 노드의 복제는 비동기이며 공통 저장 기반의 장애와 백업 복구는 별도 문제로 남깁니다.

## 출발 주소를 관측한 뒤 허용 범위 결정

DGX Pod의 주소를 그대로 LB 허용 목록에 넣지 않았습니다. 일반 Pod에서 DNS 이름으로 접속하고 DGX 외부 인터페이스와 LB 측의 제한된 패킷 헤더를 대조해 노드 주소로 변환된 경로를 확인했습니다. LB와 보안그룹의 외부 접근은 확인한 DGX 노드 및 제어 클라이언트의 단일 주소로 제한했습니다.

이 주소 제한은 노드 단위의 네트워크 범위이며 Pod나 DB 사용자의 신원을 증명하지 않습니다. PostgreSQL은 별도로 서버 신원 검증, 클라이언트 인증서, SCRAM 계정 인증과 SQL 권한을 적용합니다. [G5 사례 문서](g5-postgresql-ha.md)에서 데이터 경로와 임시 자격 증명 전달·정리 절차를 함께 설명합니다.
