# 설계 판단 기록

## 외부 1GbE와 내부 10GbE 분리

보유 서버의 NIC·CPU·RAM·SSD와 기존 스위치 사양을 검토했습니다. 기존 1GbE 스위치에 Ceph 복제·스토리지 I/O·API 트래픽을 함께 싣는 대신 외부 접속 경로는 유지하고 별도 10GbE 내부망을 구성했습니다. 이는 부하 집중 가능성을 고려한 설계이며 실측 처리량 향상률은 제시하지 않습니다.

## 기존 구성을 유지한 Octavia 관리망 확장

Neutron 논리망은 있었지만 Controller와 Amphora 사이의 관리 L2 경로가 미완성이었습니다. 처음에는 내부망 구조 변경 부담 때문에 기존 외부망을 이용하려 했습니다. 서버실 담당자에게 문의했으나 외부 업체가 설치한 스위치의 관리자 정보를 확보할 수 없어 필요한 설정을 할 수 없었습니다.

내부망을 다시 검토한 결과, 기존 관리 IP와 VXLAN 경로를 그대로 두고 VLAN 경로만 추가할 수 있었습니다. 기존 외부망의 Linux bridge·veth·OVS 연결 방식을 참고해 구성했습니다.

Linux VLAN 인터페이스가 태그를 처리한 뒤 OVS와 연결하므로 Neutron에서는 별도 physnet의 flat 네트워크로 표현합니다. 검토 중의 직접 OVS 연결 후보나 Kolla 자동 관리 인터페이스 후보를 최종 구현과 혼동하지 않습니다.

기존 관리·외부망 설정을 유지한 채 필요한 L2 경로를 추가했고 LoadBalancer 생성·상태·삭제를 검증했습니다. 무중단 보장이나 모든 기존 서비스의 무영향 실증으로 확대하지 않습니다.

## GPU 장비의 독립 클러스터

GPU 장비를 Nova compute나 기존 관리 클러스터의 worker로 넣지 않고 별도 단일 노드 Kubernetes로 구성했습니다. 가상화 기반 자원 제공 영역과 GPU 실행 영역을 분리하고 관리·서비스 경로를 연결하는 방식입니다. 단일 노드 장애 내성은 제공하지 않습니다.

## Local SSD와 외부 DB의 역할 구분

모델 파일은 로컬에 보존해 재사용 시 대용량 파일의 반복 전송을 줄이고, AI DB는 외부 OpenStack에 분리 배치하도록 설계했습니다. DB 요청은 여전히 네트워크를 사용하므로 모든 I/O를 로컬화하거나 전체 서비스 지연을 제거한 구조는 아닙니다.

## 최신 정보 제공을 우선한 크롤링 정책

구성원과 저장에 따른 조회 효율을 검토했으나, 공지사항의 최신성이라는 서비스 목적을 우선해 크롤링 결과를 영구 저장하지 않기로 합의했습니다.
